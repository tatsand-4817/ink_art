# インクアート

水面に落としたインクが広がる模様を、WebGL2 の流体シミュレーションでリアルタイムに再現するアート制作アプリ。

要件定義は [`docs/requirements.md`](./docs/requirements.md)。

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # 型チェック + 本番ビルド
```

## 現在の実装状況

| # | 機能 | 状態 |
|---|---|---|
| F-1 | 流体シミュレーション | 実装済み |
| F-2 | インク投下操作(タップ/ドラッグ) | 実装済み |
| F-5 | 混色 | 実装済み |
| F-3 | インク色選択 | 実装済み(プリセット 4 テーマ + HEX / RGB / HSL) |
| F-4 | 台紙の色選択 | 実装済み(プリセット + HEX / RGB / HSL) |
| N-2 | インクの量調整 | 実装済み |
| F-6〜F-9 | 保存・共有・クリア・PWA | 未着手 |

プリセットの色定義そのものは彩さんの確定までの**暫定**(`src/palette.ts`)。
UI と同期のしくみは本実装なので、色の値だけ差し替えれば済む。
「消す」ボタンは、コアの挙動を繰り返し確かめるために置いてある仮のもので、F-8 の正式実装ではない。

## 設計上の判断

### 染料場は「吸光度 + 顔料の量」で持つ(F-5)

要件定義では染料場を RGB 3 チャンネルで持ち、加算/ブレンドで混色させるとある。
ただし RGB を素朴に加算すると**加法混色**になり、青 + 黄 が白っぽく濁ってしまう。
実際のインクは光を吸収する減法混色なので、そのままでは「本物志向」から外れる。

そこで染料場(RGBA)にはこの 2 つを蓄えている。

| 成分 | 中身 |
|---|---|
| `rgb` | Beer–Lambert の**吸光度**。投下時に `-log(linear(インク色))` を加算 |
| `a` | **顔料の量**。どれだけインクが乗っているか |

描画時はここから 2 つの色を作って混ぜる。

```
台紙に透けた色 = 台紙の色 * exp(-吸光度)
顔料自身の色   = exp(-吸光度 / 顔料の量)
被覆率         = 1 - exp(-顔料の量 * coverage)
表示色         = mix(台紙に透けた色, 顔料自身の色, 被覆率)
```

吸光度が加算されるということは透過率が乗算されるということなので、
重なった部分は自動的に**減法混色**になる。青 + 黄 は緑になる。

量を別に持っている理由は白インク。白は何も吸収しないので吸光度が全チャンネル 0 になり、
量を数えないと「インクが無い」と区別が付かず、黒い台紙の上に置けない。
また台紙が黒いと `黒 * 透過率` はどうやっても黒なので、
顔料自身の色を別に立てないとどの色も出せない。

吸光度を量で割ると「濃度 1 のときの色」に戻る、というのがこの形の要。
おかげで副次的に、同じ色を何度重ねても黒に潰れずそのインク自身の色に収束する
(顔料を厚く盛っても顔料の色になるだけ、という実際の挙動と一致する)。
白インクを他の色に重ねると薄まる、という混ぜ方も自然に出る。

`inkStrength = 1`(原液)のときインクの芯の色がスウォッチの色とほぼ一致する。
検証時の実測値:

| インク | スウォッチ | 白台紙での芯 | 黒台紙での芯 |
|---|---|---|---|
| 白 | `#ffffff` | `#ffffff` | `#f0f0f0` |
| 空 | `#35b6f0` | `#38befa` | `#31abe2` |
| 珊瑚 | `#ff6b5b` | `#ff705f` | `#f06455` |
| 向日葵 | `#ffc93c` | `#ffd13f` | `#f0bd38` |

向日葵と空を重ねた境界は `#76c581`(緑)、
珊瑚に白を重ねると `#ff705f` → `#ffab9f` と淡くなることを確認済み。

白台紙に白インクを落とすと色の上では何も起きないが、
陰影付けを吸光度ではなく顔料の量から取っているので、
うっすら浮き出しのような凹凸だけが残る。

### HSL だけ状態として持つ(F-3 / F-4)

色の正は HEX 一本にしたいところだが、HSL だけは RGB からの派生値にできない。
彩度 0 の無彩色や真っ黒・真っ白では色相が定義できず、
RGB から復元するたびに色相が 0 に飛んでしまうためで、
彩度スライダーを 0 まで下げて戻すと色が変わってしまう。

そこでカスタム入力の中でだけ HSL を状態として保持し、
外から色が変わったときに書き戻している。書き戻しは
「いま持っている HSL から作った HEX と一致するなら何もしない」で止めており、
これが無いと往復の丸めで色相がじりじり動く。

実測での確認:

| 操作 | HEX | RGB | HSL |
|---|---|---|---|
| HEX に `#ff6b5b` | `#ff6b5b` | 255 / 107 / 91 | 6° / 100% / 68% |
| G を 200 に | `#ffc85b` | 255 / 200 / 91 | 40° / 100% / 68% |
| H を 270 に | `#ad5bff` | 173 / 91 / 255 | 270° / 100% / 68% |
| L を 30 に | `#4d0099` | 77 / 0 / 153 | 270° / 100% / 30% |

彩度を 0 に落としてから色相を 210 に動かし、彩度を 80 に戻すと `#0f4d8a`。
色相が保たれている。

### 一筆の濃さは移動距離で決める(F-2)

ドラッグ中はポインタイベントごとにインクを落とすが、その量をイベント数に比例させると
120Hz 端末で同じ操作をしただけでインクが倍載り、真っ黒に潰れる。
半径 2 つ分だけ動けば一滴と同じ濃さになるよう、移動距離で正規化している。

### タップ時に外向きの流れを作る

静止したタップは速度が 0 なので、そのままだとインクがその場で丸く滲むだけになる。
着水点の周囲に 8 方向の外向きの流れを一瞬だけ加えて、水面を押しのける挙動を出している
(`config.dropImpulse`)。

### 渦(渦度閉じ込め)と、グリッドの目が出る問題

Stable Fluids は数値粘性で小さな渦が潰れる。カールを求めて渦を押し戻すパスを
入れており、「渦を巻く」挙動はほぼこれが担っている。`config.curl` で調整。

このパスは放っておくと**速度場グリッド 1 セル分の細かい揺らぎを拾って増幅する**。
染料場は速度場の 8 倍細かいので、その増幅されたグリッドの目がそのまま転写され、
遊んでいるうちに滲みの縁がギザギザに崩れていく。
`curl` を 0 と 30 で比べると差は歴然で、0 なら完全になめらか、30 では
角ばった階段状の面が出る。

原因は 2 か所あり、両方直してある。

1. **渦を押し戻す向きの求め方**。`|渦度|` の勾配を上下左右 4 点の差分で取ると、
   1 セル分のノイズがそのまま向きになる。8 近傍の Sobel は平滑化しながら
   微分するので、この増幅が起きない。加えて、勾配がほぼ無い平坦な場所で
   単位ベクトルを立てないよう正規化に下駄を履かせている
2. **移流時の速度場の読み方**。速度場は染料場より粗いため、素直な線形補間だと
   テクセルの境目で微分が不連続になり、その折れ目が毎フレーム染料に転写される。
   補間の重みを smoothstep に置き換えると折れ目が消える。
   読み出し回数は 1 回のままなので負荷は変わらない

滲みの拡散も、上下左右 4 点平均から半テクセルずらした 4 点に変えてある。
前者は縦横にだけよく広がる異方性の強い形で、何千回も重ねると縁が菱形に角張る。
後者はハードウェアの線形補間が各点で 2x2 を平均してくれるので、
同じ読み出し回数で等方的な 3x3 になる。

### フォーマット選定

`EXT_color_buffer_float` / `EXT_color_buffer_half_float` を有効化した上で、
実際に FBO を作って `checkFramebufferStatus` で**実測**して決めている。
拡張の有無だけを見ると嘘をつく実装があるため。
half float を優先(iOS Safari 向け、かつ WebGL2 コアで線形補間可)、
駄目なら float、線形補間が使えない場合はシェーダ側の手動補間に切り替わる。

シミュレーション解像度と表示解像度は分離済み(`simResolution` / `dyeResolution`)。

### 表示は端末の等倍で描く

`devicePixelRatio` を 2 で頭打ちにしていたところ、dpr 3 の端末では
キャンバス(804x1748)をブラウザが 1.5 倍に引き伸ばして表示することになり、
細い筋にピクセルの階段が見えていた。流れが止まると特に目立つ。

重いパスは染料場・速度場の解像度で回るので、キャンバスの画素数が効くのは
最後の表示パスだけ。実測でもキャンバス面積 2.25 倍に対して負荷の増加は
12% に留まったため、`maxPixelRatio` を 3 に上げて等倍で描くようにした。

そのかわり画面が大きいほど等倍の負荷が効いてくるので、
`maxCanvasPixels`(既定 420 万)で総ピクセル数に上限を設けている。
超える場合は比率のほうを落とす。

### 陰影は広めの基線で取る

顔料の量の勾配から陰影を付けているが、勾配を隣接テクセルで取ると
染料場 1 テクセル分のムラをそのまま明暗に増幅してしまい、
流れが止まったときに細かい粒として残る。微分は高周波を持ち上げるため。

斜め 1.5 テクセル先の 4 点から勾配を取るようにした。半端な位置を読むと
ハードウェアの線形補間が各点で 2x2 を平均してくれるうえ、
基線が 3 テクセルに広がるので、本当の起伏だけが拾える。読み出し回数は 4 回のまま。

`shading` はコンパイル時の分岐から uniform に変えてあるので、
実行中に強度を 0〜1 で振れる(`__inkSim.updateConfig({ shading: 0.5 })`)。

## チューニング

すべて `src/fluid/config.ts`。開発ビルドでは `window.__inkSim` からも触れる。

```js
__inkSim.updateConfig({ curl: 20, dyeDiffusion: 0.02, shading: 0.5 });
__inkSim.simulationSize  // 実際のシミュレーション解像度
__inkSim.dyeSize         // 実際の染料場の解像度
__inkSim.precision       // 'half-float' | 'float'
__inkSim.samplePixel(0.5, 0.5)  // 表示色を 1 ピクセル読む(混色の確認用)
```

減衰率の半減期はおよそ `ln2 / 係数` 秒。`densityDissipation: 0.003` で約 4 分。
`coverage` を下げると台紙が透けて水彩寄りに、上げると顔料が前に出て不透明寄りになる。

`inkStrength`(インクの量)は UI のスライダーから触れる。範囲は 0.1〜1.5。
1.5 で頭打ちにしているのは、それ以上盛っても被覆率が飽和して一滴の見た目が
変わらなくなるため。実測値:

| 量 | 空インクの芯 |
|---|---|
| 10% | `#cfeffd` |
| 50% | `#5dcaf8` |
| 100% | `#38befa` |
| 150% | `#35bbf9` |
